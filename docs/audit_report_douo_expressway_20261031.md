# 道央自動車道 パイロットテスト検証レポート

- **実施日**: 2026-10-30 〜 2026-10-31
- **検証対象**: 道央自動車道（E5, 430.6 km、七飯藤城IC ➔ 名寄IC）
- **作業領域**: 隔離テスト環境（`data/test/douo_highway_test/`）および検証Webコンソール（`web/explorer/audit_douo.html`）
- **文書位置づけ**: 国土数値情報（KSJ）におけるSA/PA欠落問題の解消策検証、オープンデータ（Wikipedia/Wikidata/OSM）調達パイプラインの実証、非AI決定論的論理検査および画面検査の確立、ならびに専門家監査に基づくプロジェクト全体への提言書。

---

## 1. 検証の背景と目的

### 1.1 背景（KSJデータの欠損発覚）
北海道回廊パイロット設計に伴い、既存の日本マスタデータ（`data/master/nodes.csv`）を点検した結果、高速道路の「パーキングエリア（PA）」が全国で1件も収録されておらず、「サービスエリア（SA）」もスマートIC併設箇所等30件しか存在しないことが判明した。
調査の結果、一次調達元である国土交通省・国土数値情報（KSJ N06）は「交差・分岐点（Joints）」のみを定義しており、本線上の単独SA/PAが構造上除外されていたことが原因と特定された。

### 1.2 検証目的
本番マスタ（`data/master/`）を汚染させない完全隔離テスト環境において、以下の4点を実証すること：
1. **オープンデータ連携**: Wikipedia、Wikidata、OpenStreetMap（OSM）を組み合わせ、SA/PA・スマートIC・本線料金所・バスストップを含む全施設を欠落なく網羅できるか。
2. **トポロジーモデリング**: 起点から終点まで途切れのない1本の有向一筆書きチェーン（エッジ網）を構築できるか。
3. **決定論的論理検査**: AIの推論に頼らず、純粋なプログラム（数学・幾何・トポロジー規則）のみでデータの欠陥を自動検出できるか。
4. **画面検査コンソール**: 人間が疲れずに直感的に誤りを発見できるWeb照合UIを実現できるか。

## 2. 構築データセットと調達パイプライン

### 2.1 成果データファイル一覧（`data/test/douo_highway_test/`）
- **`test_all_highway_nodes.csv` (全70施設)**:
  - IC・JCT・SIC: 44件
  - SA・PA・展望所: 19件（従来の欠落を完全補完）
  - 単独バスストップ: 7件
- **`test_all_highway_edges.csv` (全69区間)**:
  - 七飯藤城ICから名寄ICまで連続する有向接続エッジ
- **`test_sapa_nodes.csv` (16件)**:
  - ユーザー指示に基づき、初期抽出のSA/PA単独データを保全したもの
- **`test_all_transport_routes.csv` (1件)**:
  - 路線メタデータ（`TEST-RT-DOUO-EXP-ALL`）

### 2.2 稼働ステータス（時間軸）の3分類
将来の過去データ（変遷）管理を見据え、施設を3状態に分類定義：
1. **供用中 (active)**: 63件（現役で稼働・営業中の施設）
2. **計画・事業中 (planned)**: 5件（七飯藤城IC、七飯IC仮称、駒ケ岳PA、山崎PA、温根別PA）
3. **廃止・休止 (closed)**: 2件（樽前BS [2018年廃止]、北恵庭BS [2012年廃止]）

### 2.3 データソース別の評価と役割分担
- **Wikipedia（日本語版）**: 路線記事のインターチェンジ表から「走行順序」「公称キロ程」「IC番号」「接続路線名」「設備（BS/GS/SIC/TB）」を高精度に抽出。路線の順序保証において最も優秀。
- **Wikidata（SPARQL API）**: `P361 = Q867982`（上位: 道央道）でクエリし、世界一意のQID、Point(経度, 緯度)座標、開通日（P571）を結合。
- **OpenStreetMap（Overpass API）**: パブリックAPIサーバーのHTTP 406/502制限が厳しく、連続自動調達の主軸には不適。Wikidata・Wikipedia先行が堅牢。

## 3. 検査体制の検証結果

### 3.1 プログラムによる決定論的論理検査（Gate 1〜4）
スクリプト `validate_douo_logic.ps1` を作成し、4段階の検査を実施。結果は **ALL PASS (0エラー, 0警告)** を達成。
- **Gate 1（スキーマ・実体参照）**: 列数整合、未処理HTMLタグ・実体参照混入ゼロ
- **Gate 2（外部キー・境界）**: ノードID/路線ID/自治体IDの実在性、北海道BBOX（緯度41.0〜46.0, 経度139.0〜146.0）逸脱ゼロ
- **Gate 3（ネットワーク接続性）**: エッジ順序1..69の欠番なし、前区間終点と次区間起点の完全一致（トポロジー断絶ゼロ）、路線起終点との完全合致
- **Gate 4（幾何・距離検算）**: ゼロ距離・負距離ゼロ、Haversine直線距離と道路距離の対照（逆転現象なし）

### 3.2 画面検査Webコンソール（`web/explorer/audit_douo.html`）
- **左ペイン（路線図のシンプル化）**:
  - 情報過多を排し、アイコン（IC/SA/PA/BS/JCT）＋施設名＋番号のみを縦型表示。
  - 「🟢 供用中のみ (63件)」「全表示 (70件)」「計画中」「廃止」をワンクリック切り替え可能。
- **ノード／エッジの独立選択**:
  - ノード選択時は施設属性・Wikipedia諸元・前後3施設ミニ対照表を表示し、地図ピンにパン。
  - エッジ選択時は区間距離・大圏直線距離・屈曲率・両端ノードを表示し、地図上に区間を太線ハイライト。
- **引用元URLの直結**:
  - Wikipedia「道央自動車道」元記事および各施設個別記事への外部リンクを常時配備。

## 4. 専門家監査で判明した課題・問題点

自動論理検査が「ALL PASS」となった一方で、実データ詳細監査により**論理検査をすり抜けた欠陥が5点**特定された。

| No | 項目 | 検出された問題点 | 発生原因 |
| :--- | :--- | :--- | :--- |
| **1** | **edges.csv スキーマ不整合** | 本番マスタと列構成が異なっていた（本番の `開始日,終了日,確定ステータス` が抜け、`距離_km,軌道種別,備考` に置換）。 | Gate 1が列数（9列）のみを検査し、**列名の一致検査**を怠っていた。 |
| **2** | **供用中施設の座標抜け** | 2020年供用済の「苫小牧中央IC」および「七飯藤城IC」の緯度経度・Wikidata IDが空欄。 | Wikidata側の上位関係（P361）登録漏れ＋Gate 2が「座標がある場合のみ範囲検査する」仕様だったため欠損を検知できず。 |
| **3** | **自治体コードの誤判定** | 「森IC（本来森町）」が七飯町に、「伊達IC（本来伊達市）」が洞爺湖町に誤登録。 | Wikipedia表の `rowspan`（行結合）やパイプ付きリンクの解析処理が自治体切り替わりを取りこぼした。 |
| **4** | **非供用ノード非表示時の距離欠落** | 「供用中のみ」表示にすると、間に計画施設（駒ケ岳PA等）を挟む現役IC間（大沼公園〜森）の距離が「計画中（―）」になる。 | エッジを静的な2点間距離のみで保持していたため。 |
| **5** | **備考カラムへの属性詰め込み** | IC番号（`[6]`）や起点累計キロ程（`10km`）が独立カラムではなく `備考` に文字列で結合されていた。 | ノード正規スキーマ外の属性の格納場所が暫定処理されていた。 |

## 5. プロジェクト全体（全交通網・全世界・全時代）への提言（5大設計原則）

本パイロットの成果と反省から導かれた、今後の全世界・全交通網展開における必須ルール：

### 原則1：時代・表示切替で破綻しない「累計キロ程（KP）方式」
- 各ノードに起点からの「累計キロ程（KP）」を持たせる。
- 計画中施設や過去の廃駅を非表示にした際、表示されている前後のノードの累計キロ程を引き算（`終点KP - 起点KP`）することで、どの時代・どのフィルター状態でも正しい区間距離とエッジを動的生成できる。

### 原則2：オープンデータ調達の「3段階補完パイプライン」
1. **順序・路線構造**: Wikipedia路線表から抽出（人間の手による路線順序が最も信頼できる）。
2. **座標・ID取得の2段構え**:
   - 第1段: Wikidata SPARQL一括取得。
   - 第2段（漏れ対策）: Wikipedia個別記事タイトルからMediaWiki API経由で直接Wikidata QIDと座標（`prop=coordinates|pageprops`）を個別回収する。
3. **自治体の決定**: 不安定な表の `rowspan` 解析を全廃し、**「取得した緯度経度と自治体境界の空間判定」**または**「施設のWikidataプロパティ（P131: 行政区画）」**から確定する。

### 原則3：決定論的論理検査（Gate 1〜4）の必須項目拡張
- **Gate 1**: 列数だけでなく「ヘッダー列名の完全一致」を義務付け。
- **Gate 2**: 「供用中（または廃止）施設なのに座標が空欄の場合はエラー」とする座標必須化ルールを追加。
- **Gate 4**: $\text{屈曲率} = \text{道路距離} \div \text{大圏直線距離}$ を計算し、**1.0未満（直線より短い＝物理的破綻）** または **3.0超（座標ワープ・取り違え）** を機械的に不合格とする。

### 原則4：原典URL（トレーサビリティ）の2階層保持
- 路線全体: `transport_routes.csv` に路線記事URL（Wikipedia本編や公的台帳）を保持。
- 拠点個別: `nodes.csv` の `Wikipedia_url` に施設個別記事URLを必ず格納。

### 原則5：画面検査UIの標準テンプレート化
- 左ペイン: アイコン＋名称＋番号の極小構成タイムライン（供用中/計画/廃止の即時切替）。
- ノード（点）とエッジ（線）の独立選択・右ペイン詳細連動。
- 右ペイン: システムDB値と整形済み原典データ（＋前後ミニ路線表＋原典直結ボタン）の横並び対照。

## 6. 結論と次期アクション

本パイロットにより、公的データの欠損をオープンデータで完全に補完し、高品質なネットワークデータを量産するための技術仕様・検査仕様が確立された。
検出された5つの課題に対する是正ルールを共通スクリプト群（`tools/`、`scripts/validators/`）および本番収集仕様へ反映した上で、北海道回廊パイロット（函館本線・国道5号/12号）および全国・海外展開へ移行することを提言する。
